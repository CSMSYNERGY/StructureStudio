# My Synergy Phone: portal-side deviations and additions

This file covers the portal builder's part of My Synergy Phone: `portal/**`, `supabase/functions/portal-settings/**`, `_shared/crmFeed.ts`, `sms-inbound/**` and `tests/phone`, `tests/harness/mySynergyPhone.mjs`. The contract is `structure-studio-phone/docs/SPEC.md`. It sits under `supabase/` because the static web host never serves that folder (see `.assetsignore`).

## Things other builders need to know

1. **"Sign out all devices" ends the person's Supabase sessions.** `phone_signout_user` bumps `phone_user_settings.device_generation`, which retires every registered identity. That alone doesn't secure a lost phone: a device that is still signed in to Supabase just asks `/token` again and gets a token on the new generation. supabase-js has no admin "sign out user X" (`auth.admin.signOut` needs that user's own JWT), so the handler also calls `rpc('phone_end_user_sessions', { p_user_id })`, which migration 254 PART 6B now defines: `returns integer`, `security definer`, deletes the user's `auth.sessions` rows (refresh tokens and MFA claims cascade), `service_role` only. The answer carries `sessionsEnded` and `sessionCount`. On a database without 254 the call returns PGRST202, the action answers `sessionsEnded: false`, and the screen tells the owner to also change that person's password. Three additions: the person's `phone_devices` rows are deleted too (the Worker's own `/devices/signout-all` does the same, so text alerts stop reaching a lost phone); an admin can't do this to an owner, because ending sessions signs the person out of Structure Studio everywhere (an owner can, and so can a platform operator); and **a CSM Synergy operator's team row keeps its sessions** unless the caller is an operator too (review SSB-9). Operators' sign-ins cover every tenant they support and the operator tools, and live, four `app_operators` have `client_users` rows. Their My Synergy Phone devices on this team are still retired; the answer says `sessionsKept: "operator"` and the screen explains it. If the `app_operators` read fails, sessions are kept (fails closed). The rules are `signoutPlan` and `bumpDeviceGeneration` in `phone.ts`, driven by `tests/phone/phoneReview_test.ts`.
2. **Mobile deep link.** On a phone's browser, Call opens `mysynergyphone://call?to=<E.164>&contact_id=<uuid>&user_id=<uuid>&client_id=<slug>&ts=<epoch ms>` (SPEC section 7). The first four are the extension message's fields, so the app refuses a different signed-in person the same way; `ts` is `Date.now()` when the page made the link, and the app drops a link more than a minute old (or ahead), so a replayed link never offers a call nobody just asked for. The scheme changed with the 2026-10-01 rename, and the renamed app is a new install (new package id), so an app build from before the rename never answers this link: put a renamed build on the pilot phones when this portal change ships.
3. **Extension IDs and store links.** `window.SS_PHONE_EXTENSION_IDS` defaults to `["deoplohngfikappgihmmofhfhhdcpkch", "ipiccbfkkbenmiaiaoecbhbjalkbikjk"]` in `portal/01-core.jsx`: the Chrome Web Store id first, so a store install wins, then the unpacked dev build's id (stable because that build carries a fixed manifest `key`; the store upload has the `key` removed, since the store refuses it). Only real Chrome ID shapes (`/^[a-p]{32}$/`) are ever messaged, and the extension checks the page's origin itself. `SS_PHONE_LINKS` holds the store links, still placeholders: a link that says PLACEHOLDER shows as "link coming soon" instead of linking to a missing page.
4. **The `status` action now returns `phoneStatus`** (`"on" | "off" | null`). This is a separate read that tolerates errors, and it only runs for callers with phone access. If portal-settings deploys before migration 254, the bootstrap keeps working and the answer is `null` (treated as off).
5. **`crm_create_contact` ("Save as contact") exists.** Body `{name, phone: "<E.164>", source: "phone"}`, answer `{ok: true, id, contactId, relinked: {calls, sms}}`. It's gated contacts:'edit' and sits behind the CRM subscription like every `crm_*` action. It's one call to the SQL function `crm_create_contact` (254 PART 9B), which inserts the contact and moves this tenant's earlier `phone_calls` and `sms_messages` rows with no contact and a matching number onto it, **only the rows nobody loses and nobody gains** (254 DEVIATION 14, review SSB-6): a call moves only if every team member on it can see the new contact afterwards, and a saver limited to their own customers moves only calls they were on and texts they sent. Rows left behind stay unlinked, still visible to the people on them. `tests/sql/migration254.test.cjs` drives the two-reps-one-number case. A caller limited to their own customers becomes the owner; everyone else leaves it unassigned (the design path, `crm_ensure_contact`, assigns nobody either). A duplicate number answers 409 with `crm_save_contact`'s sentence, from one shared constant (`DUPLICATE_PHONE_SENTENCE` in `phone.ts`). CONTACT_ROW_SCOPE has a new rule kind, `creates: true`, which lets a narrowed caller through because the branch makes them the owner.
6. **Plan phase 6 actions, all phone:'edit':** `phone_search_numbers` (`{areaCode?}`), `phone_buy_number` (`{phoneNumber}`) and `phone_enable_number` (no body). `phone_settings_get` also returns `canBuyNumber`, `numbersForSale`, `voiceSetup`, `canSwitchOn`, `canConnect`, `selfServe` and `number.callingOnly`. The Twilio half is in `phoneNumber.ts`, which has no network of its own (fetch and the Twilio helpers are injected) and is unit-tested against stubs: `buyCallingNumber` (the whole purchase) and `switchCalling` (the on/off switch and what it does to the number).
7. **Edge env.** For "Connect this number for calls": `PHONE_API_BASE` (default `https://phone.structurestudiosuite.com`), `PHONE_WEBHOOK_SECRET` (the Worker's `?key=`), and `PHONE_FALLBACK_URL` (the TwiML Bin that plays the greeting and records; the Worker's recording sweep files those messages). Connecting is refused, with a 503 refusal, until the secret and the fallback are set. A number inside a builder's own Twilio sub-account (Workstream 2) uses `TWILIO_SUB_VOICEMAIL_URL` instead, fetched with GET: `PHONE_FALLBACK_URL` is a TwiML Bin, and a Bin answers only the account that owns it (phone-api SETUP.md 7f). Buying a number additionally needs `SMS_INBOUND_SECRET` (the project-wide secret sms-inbound already uses) and the Twilio credentials, checked before any money moves. **`PHONE_SELF_SERVE`**: unset (off) until builder launch; see the rollout item below.
8. **The portal's `window.SS_PHONE_API_BASE`** (01-core.jsx, next to `SS_PHONE_EXTENSION_IDS`) defaults to the same address. The contact timeline plays a voicemail from `<SS_PHONE_API_BASE>/voicemails/<id>/audio`, **fetched with the session in the `Authorization` header and played from a `blob:` URL** (`ssPhoneFetchVoicemail`, `SsVoicemailPlayer` in 02-sales.jsx), only when Play is pressed, only for someone with phone access, with calling on, outside view-as, and while the recording exists (`meta.voicemailDeleted`). It used to be an `<audio src>` carrying `?access_token=<session>`; the Worker's request logs (observability on) kept every such URL, so a live session token landed in Cloudflare's logs on every play (review SSB-7). The Worker's CORS already allows the portal hosts with `authorization`. **For the phone-api owner:** once nothing sends `?access_token=` any more, `requireCaller(..., { allowQueryToken: true })` on `/voicemails/:id/audio` can go.
9. **Texting adopts a calling-only number (done 2026-09-29).** A number bought on the Phone tab is an `sms_numbers` row with `messaging_service_sid` NULL and `registration_status` 'pending_registration'. portal-sms's `buy_number` now reads the tenant's live rows (`adoptNumber.ts buyPlan`): none buys as before; one already in a Messaging Service refuses as before; otherwise the oldest calling-only row is **adopted** (`adoptCallingNumber`): its SID (or one found by its E.164), into the builder's Messaging Service unless it is already there (`_shared numberInService` / `attachNumberToService`, the helper `purchaseNumber` now uses too), its own SmsUrl cleared (the service's inbound URL is sms-inbound too), then `client_settings.sms_number`, the registration `campaign_approved → number_pending`, and last the row's `messaging_service_sid`, so a failure before that leaves a row the next press adopts again. Adoption runs only at `campaign_approved` (or a retry at `number_pending`/`active`), takes **no wallet hold** (the Phone tab held the first month under `sms_num:<client>:<number>`) and buys nothing. A failed live-number read now refuses (503) where the old count read as "no numbers" and went on to buy. The SMS tab offers "Use this number for texting" instead of the search when a calling-only number exists; `status` projects `numbers[].callingOnly`. `PHONE_SELF_SERVE` no longer has to wait for this; turning it on is the launch decision. (`purchaseNumber` still does not take the voice settings: the texting purchase leaves voice alone, and "Connect this number for calls" sets them.)
10. **A calling-only number's texts go to sms-inbound** (review SSB-3). With no messaging service, Twilio uses the number's own SmsUrl, and an empty one dropped every reply at Twilio. The purchase sets `SmsUrl` (`${SUPABASE_URL}/functions/v1/sms-inbound?key=${SMS_INBOUND_SECRET}`, byte for byte what portal-sms puts on a Messaging Service and what sms-inbound rebuilds to check the signature) in the same Twilio update as its voice settings, and "Connect this number for calls" sets it again for any number with no messaging service, which repairs a number whose purchase-time update failed. A number inside a Messaging Service is never given an SmsUrl.
11. **The purchase adopts ANY unrecorded number and gives back one it cannot record** (review SSB-4). A number bought with its response lost, or bought and then not recorded, is gone from Twilio's search, so the next press picks a different one; matching only the pick bought that one too. Now every `FriendlyName=<client_id>` number Twilio lists (the tenant has no live row by then) is adopted, the pick if it is among them, else the first, and the answer carries a `note` saying so. If the `sms_numbers` insert fails after a fresh purchase, the number is released at Twilio and the hold released; an adopted number is never released there.
12. **The contact timeline shows calls by phone level** (review SSB-5). `crm_record` and `crm_feed` are gated on contacts or designs, which says nothing about calls, so every call and voicemail transcript on a contact reached anyone who could open it. `buildCrmFeed` now takes `phone: {level, userId, contactOwner}` (`phoneFeedScope` in index.ts, from `canRead("phone")` and `ownPhoneOnly`): `none` (or absent, failing closed) reads no `phone_calls` at all; `own` keeps only the viewer's own calls (`crmFeed.ts callVisibleToOwn`, the Worker's `callIsMine` plus `transferred_from`, pinned against the Worker's source in the tests); literal view/edit sees them all. The voicemail player only ever appears on a line that survived, so it no longer offers a teammate's voicemail the Worker would 404.
13. **Tests, now in the gate.** `tests/phone/*.ts` (Deno; `deno test --node-modules-dir=none --allow-read --allow-env tests/phone/`) and `tests/sql/*.test.cjs` (Node + PGlite: `migration254.test.cjs` applies 254 to an in-memory Postgres and drives its RPCs, triggers, policies and the Save-as-contact scope; `migration255.test.cjs` applies 255 on the live `sms_numbers` shape). `scripts/preflight.mjs` runs `tests/phone` as a third deno test group (from the repo root, with those flags), and runs every `tests/sql/*.test.cjs` **only when `tests/sql/node_modules` exists** (`npm install --prefix tests/sql` once); otherwise it prints `preflight: migration tests SKIPPED — …` and blocks nothing, so the pre-push gate never needs a network install. `--self-test` proves the group is found and run from the root, and that the SQL step skips, fails and passes the right way.

14. **Caller-ID trust (plan section 14, phase 6): `phone_trust_setup` and `phone_trust_status`, OPERATOR-ONLY.** Both refuse anyone who is not a CSM Synergy operator who can write (an operator in view-as with `can_write`, or an `app_operators` member with `can_write` on their own tenant; a `support_only` operator is refused either way), first thing, and both are `phone:edit` in GATES (status writes the row, and a view-level line is where resolveTenant lets a read-only operator through), and `PHONE_SELF_SERVE` never opens them: each one submits the builder's legal identity for a Twilio review, and nothing runs them on a timer or a webhook. `phone_trust_setup` `{product: "shaken_stir" (default) | "voice_integrity", voiceIntegrity?: {useCase, employeeCount, averageDailyCalls, notes}}` puts the tenant's number on its business profile (the Secondary Customer Profile the texting registration made; for an **internal** tenant with none, or whose number is already on it, `TWILIO_PRIMARY_PROFILE_SID`, since a number sits on one business profile; a customer is never put on the primary; a failed read of the primary answers 502 and sends nothing, never a guess), then creates or reuses the Trust Product (SHAKEN/STIR policy `RN7a97559e…`, Voice Integrity `RN5b3660f9…`, both from Twilio's ISV guides), assigns the profile (and for Voice Integrity a `voice_integrity_information` EndUser) and the number to it, and submits it (`Status=pending-review`) unless it is already under review or approved. A Voice Integrity resubmit (draft or `twilio-rejected`) that carries answers writes them onto the product's existing `voice_integrity_information` EndUser (`POST EndUsers/{IT}` Attributes) before resubmitting. One run per number at a time: the setup first claims `sms_numbers.caller_id_lock_until` (migration 255) in one conditional update and answers 409 while another run holds it. It refuses (409) unless the business profile is `twilio-approved`. Every step is listed before it is made, the Trust Product is found by FriendlyName (`<client_id> — SHAKEN/STIR`) or by carrying the same profile before one is created, and its SID is written to the row the moment it exists. `phone_trust_status` reads each recorded product from Twilio, stores the status, clears one Twilio no longer has, and returns rejection **codes** only. The flow is `_shared/twilioTrustHub.ts setupVoiceTrust`; the order and refusals are `phoneTrust.ts`. `phone_settings_get` adds `callerId` (statuses, no SIDs; `available: false` before migration 255) and `canManageCallerId`; the Phone tab shows a Caller ID card to everyone on the team screen and the Register / Check status buttons to operators only. **Voice Integrity's price was not checked** (plan section 17 says to before phase 6); nothing here charges the builder.
15. **Migration 255 (`255_sss_phone_followups.sql`, NOT applied).** Adds `sms_numbers.shaken_trust_product_sid`, `shaken_status`, `voice_integrity_trust_product_sid`, `voice_integrity_status` and `caller_id_checked_at`, all nullable, with checks for Twilio's TrustProduct status enum and the `BU…` SID shape, apply-time assertions (columns, checks, the browser roles still hold nothing on `sms_numbers`) and a probe on one synthetic row, deleted before commit. portal-settings reads these five in their own select, so it can deploy before 255 is applied.

## Deviations from the SPEC or plan, and why

1. **Text hint in view-as.** Call uses the plan's exact hint, "Calling isn't available while viewing another account." The SMS tab says "Texting isn't available while viewing another account." instead, because "Calling" on the SMS button would read as a mistake.
2. **Rollout: enforced on the server; `ssPhoneOffered()` only draws.** Plan D9 keeps calling off for every builder until launch, and beta shares production's database, functions and Twilio account, so the browser guard alone let any builder's owner on a beta host turn calling on and buy a number (review SSB-1). Now `phone_status_set` with `on: true`, `phone_search_numbers`, `phone_buy_number` and `phone_enable_number` refuse (403, marked as a refusal) unless the caller is a CSM Synergy operator, either in view-as or an `app_operators` member with `can_write` on their own tenant (the pilot's owners), or `PHONE_SELF_SERVE=on` is set (`phoneRolloutGate`, `phone.ts phoneRolloutRefusal`). Turning calling **off** is never gated. `phone_settings_get` reports `canSwitchOn` / `canConnect` (and folds the rollout into `canBuyNumber`) so the Phone tab offers only what the server will accept, and tells an owner without the switch why. `ssPhoneOffered()` in `portal/01-core.jsx` still decides where the tab, the Calls item and the Call button are drawn (calling on, an operator viewing, or a beta or local host). ## How the Calls report counts (plan section 7)

| Column | What it counts |
|---|---|
| Calls out | Outbound calls the person placed |
| Calls in | Inbound calls that rang them (`rang_user_ids`) or that they answered, which covers transfers |
| Answered | Inbound calls they answered |
| Missed | Inbound calls that rang them and that nobody answered. Every person rung gets one. A call a teammate answered isn't a miss for the others. |
| Voicemails | The missed calls above that ended in a voicemail |
| Avg length | Average over the calls they actually talked on, so unanswered dials don't pull it down |
| Texts sent | Texts where `sent_by` is them |
| Texts received | Inbound texts on customers assigned to them. Texts from customers assigned to nobody count only in the whole-business line. |

The whole-business line counts each call once. A contacts:'own' caller only sees rows about customers they can see, plus their own calls to unknown numbers (`keepForOwnScope`).
