# phone-api: deviations from docs/SPEC.md

Where the Worker reads the contract a particular way, adds to it, or departs from the plan. Everything here is additive for clients unless it says otherwise.

## Contract additions the clients should know about

1. `/calls/:id/transfer` and `/calls/:id/events` accept a Twilio CallSid (`CA...`) as `:id`, as well as the `phone_calls` id. An outbound call cannot receive custom parameters, so the app only knows its own leg's CallSid there; the Worker resolves it through `client_call_sid` or `twilio_call_sid`, always inside the caller's tenant. On inbound calls (and transfers) every `<Client>` carries a `call_id` custom parameter with the `phone_calls` id, and transfers add `transferred_by`, `customer_e164` and `contact_id` (item 49).
2. `GET /threads` and `GET /calls` return `cursor` when there is another page. Pass it back as `?cursor=`. It is an ISO timestamp.
3. `GET /health` returns `{ok, version, deployment}`; `deployment` is the Cloudflare version id.
4. `POST /settings/me` returns `settings: {dnd, dnd_until, forward_to_cell}` (phone-core's `MySettings`). `dnd` is the effective value: a passed `dnd_until` reads as off.
5. `sent_via` on `sms_messages` is `extension` when the request's Origin is `chrome-extension://...`, otherwise `mobile`. An `x-sss-client: extension|mobile` header overrides it. The SPEC does not say how the Worker knows.
6. A preflight `/token` lasts 600 s, not 3600; the response's `ttl` says which.
7. HTTP statuses for the error codes: `unauthorized` 401; `no_phone_access`, `phone_off`, `retired_device`, `not_your_customer`, `emergency_blocked` 403; `no_consent`, `opted_out`, `number_not_registered`, `no_number` 409; `wallet_empty` 402; `minute_cap` 429; `not_found` 404; `bad_request` 400 (405 for a wrong method); `twilio_error` 502; `internal` 500. Clients switch on `code`, never the status.

## Choices where the SPEC or plan left room

8. `/token` asks Auth whether the session still exists (`GET /auth/v1/user`), in parallel with the context read, so it adds no round trip. The plan says the Worker never calls `auth.getUser()`; this is the one exception, and only on `/token`. Without it, "Sign out all devices" could not stop a lost phone from minting a fresh line while its access token lives (up to an hour). It fails open if Auth is down (logged, throttled) and closed if Auth says the session is gone. The call webhooks never call Auth.
9. The phone_calls id is generated in the Worker, and the row is written in `waitUntil` after TwiML is returned, so `/voice/inbound` stays at one database round trip before the answer. The status, voicemail and after-dial handlers retry briefly when a callback beats the insert.
10. Outbound refusals are TwiML (`<Say>` in plain English, then `<Hangup/>`), because the Voice SDK cannot read a JSON error. Where there is a tenant, the attempt is written as a `failed` `phone_calls` row with `error_code` (`not_your_customer`, `minute_cap`, `emergency_blocked`), so the app can show the reason when it re-reads the call.
11. 911 while `EMERGENCY_MODE=block`: the attempt is recorded with `is_emergency = false`. Nothing reached a dispatcher, so the 60-minute "ring only this person" rule must not switch on. It is also logged at `warn`. In `allow` mode only 911 and 933 pass (the numbers Twilio supports); 112 is still refused.
12. The 911 callback rule re-rings the person who dialed 911 for at most 10 rounds, then says "We could not reach anyone. Please call back." and hangs up. It never goes to voicemail, and it never rings forever.
13. When nobody is available, calls go straight to voicemail even if the route's `no_answer` is `forward`, as the plan says. Forwarding applies after a ring that nobody answered. A number with no `phone_routes` row rings nobody.
14. A member's `forward_to_cell` rings at the same time as their app, through the press-1 screen (the plan's "forward to a cell with a press 1 screen"). A `<Dial>` holds at most 10 nouns; apps come first, member by member.
15. Transfers: a teammate on DND is not rung at all, and the customer goes straight to the builder's voicemail. `transfer_state` is cleared when the teammate answers or when voicemail is reached (as well as by after-dial), so the teammate can transfer the call on again. `answered_by` moves to the teammate on answer; `transferred_from` keeps the person who handed it on, and both see the call in "My calls".
16. When the customer's leg of an inbound call ends while the row still says `in_progress` (a transfer that ended in voicemail), the Worker closes it as `completed` with the talk time. An outbound customer leg that is canceled before it answers is recorded as `no_answer`.
17. The daily minute cap counts outbound minutes on the UTC day, each call rounded up to a whole minute, plus the elapsed minutes of calls still going. It reads at most 1000 rows (PostgREST's cap), which is far above a builder's day.
18. `/sms/send`: portal-settings' contact/short-code match has no twin here because the API carries no short code. Its twin is the number: the recipient is read from the contact row, and the `to_e164` the app sent must match it or the send is refused. A contacts `view` user may not text a saved contact (the CRM gate is contacts `edit`), but may reply to an unknown number that texted first, as plan section 8 says. An unknown-number reply is refused when that number has since been saved as a contact.
19. `/sms/send` tags the row with `client_temp_id` and `sent_via` in a second update after `sendTenantSms` returns (SPEC section 2). `smsSend.ts` is unchanged. The insert's realtime event can arrive before the tag, so the apps should also match their optimistic bubble on the `id` this endpoint returns.
20. "Mine" for threads: a thread is mine when the contact's owner is me, when the contact has no owner, or when I sent a text in it. Unknown numbers count as unowned. Phone level `own` always gets "mine"; `view` and `edit` get it with `?mine=1`.
21. Calls with no contact (unknown numbers) are visible to contacts `view`/`edit`, and to anyone else only if they took part in the call.
22. `/voicemails/:id/audio` marks the voicemail heard (`listened_at`, `listened_by`) the first time it is played. There is no separate endpoint for that in the SPEC.
23. `/log` is rate-limited to 30 rows a minute per person per isolate, so a crash loop cannot flood `app_errors`. It stores `app_version` and `user_id` inside `context`. (Since 2026-10-03 only for the mobile app: the Chrome extension's reports store keyed refs instead, item 64.)
24. **Usage charges, one wallet line per call and per text (migration 259, 2026-10).** This replaced the daily combined minute debit (`src/cron/usageDebit.ts`, deleted; it never ran live). `src/cron/usageCharge.ts` runs every 5 minutes from the tick (minute % 5 == 2) and charges each finished call or text at Twilio's own cost times `phone_billing_settings.markup`, through `wallet_usage_debit` (idempotency key `usage:call:<id>` / `usage:sms:<id>`). Its header has the queue, the states and the request cap.
    - **Rails:** env `PHONE_USAGE_METERS` (default `off`) AND the meter armed in the database (`phone_usage_armed`: markup and `armed_at` set, the meter active or the tenant on the pilot list). A call or text before `armed_at` is never charged. Arm in that order: the env rail first, then `armed_at`.
    - **The ledger wins:** a debit whose reply was lost (or whose row update failed) is already on the ledger when its row is retried. The retry records the ledger line's own charge and cost (`wallet_usage_debit` returns them on a replay), and a retried row that would now settle as shadow, exempt or not billable is settled as charged from that line instead, with a warning (`usage_charge_kept_from_ledger`) in case it should be refunded.
    - **Billable talk:** a `completed` call with `duration_s > 0` is billed whether or not `answered_at` was written (Twilio's completed means it connected). A `missed` call waits 20 minutes before it is settled, one recording sweep, so a voicemail the sweep files late is still billed as one.
    - **Cost capture:** env `PHONE_USAGE_COST_CAPTURE` (anything but `off`; ships `on`) records every call's and text's Twilio cost, and what it would charge, as `shadow` rows in `usage_charges` while nothing is charged.
    - **Twilio's totals:** the 09:00 UTC run stores yesterday's Usage Records in `twilio_usage_daily`, to check the per-item costs against.
    - The monthly line fee moved unchanged to `src/cron/lineFee.ts` and still runs at 09:00 UTC on its two rails (item 37).
25. Voicemail retention is one Worker-wide setting (`VOICEMAIL_RETENTION_DAYS`), not per builder yet.
26. `SUPABASE_URL` is a secret, not a var, so the project ref stays out of this public repo.

## Not imported, on purpose

27. The Worker does not import `@sss/phone-core`. This repo is public and cannot depend on the private phone repo. `src/identity.ts` is a twin of phone-core's identity and E.164 helpers, and `test/identity.test.ts` compares the two on every case when `PHONE_CORE_DIR` points at a checkout (it passed against phone-core 0.1.0 on 2026-09-29).

## Not verified here

28. APNs requires HTTP/2. The APNs sender is unit-tested against a stub, but whether a Worker's `fetch` reaches `api.push.apple.com` over HTTP/2 has to be proved on a real iPhone in phase 4. If it cannot, iPhone text alerts need another path.
29. Android text alerts use notification channel `texts`. The phone app must create that channel, or Android files the alerts under its default channel.

## Added 2026-09-29: the auth-token gap and phase 5

30. **`TWILIO_AUTH_TOKEN` is optional (departs from SPEC section 1 and plan section 8, which say a missing token refuses everything).** Twilio's API never returns the auth token, so a Worker set up from API credentials may start without it. Now:
    - `PHONE_WEBHOOK_SECRET` is always required. Without it every Twilio request gets 503 (`twilio_no_webhook_secret`, error).
    - With the token set, a webhook needs both the `?key=` and a valid `X-Twilio-Signature`, as before.
    - Without the token, a webhook is accepted on the `?key=` alone, and its `AccountSid` must be present and equal `TWILIO_ACCOUNT_SID`. The first such request in each isolate logs `twilio_signature_skipped` at `warn`.

    What someone who learned the key could do while the token is unset (corrected 2026-09-29): post fake status, after-dial, voicemail, transcription and conference callbacks. That lets them write fake `phone_calls` rows, mark real calls ended in the database, and put invented text on a voicemail as its transcript. Webhook answers go back to whoever posted, so they cannot place a call.
    - **Checked against Twilio when unsigned:** the conference callback and the holder-leg backstop act only when Twilio's own call record says the leg has ended; a warm-transfer answer (`leg=warm`, which moves `answered_by` and with it the right to hold and transfer) counts only when Twilio says that leg is live, rang that user's identity, and is in this call's conference (`warm_answer_unverified` at `warn` otherwise); a missed warm leg (`leg=warm`, no-answer/busy/failed/canceled, whose CallSid is left out of the participant count) counts only when Twilio says that leg has ended and rang that user's identity (`warm_miss_unverified` at `warn` otherwise: no `warm_transfer_missed` event, and the participant list is taken as Twilio gives it).
    - **Not checked, so an insider could still listen in:** the `leg=client` answer and the `/voice/screen` press-1 set `answered_by` from the request while a call is ringing (the first ring, or a cold transfer's 20 s). Someone with the key, a login on the same tenant and the call's id could claim a ringing call that way and then transfer the customer to an account they control. Checking those two against Twilio would put a REST read on the answer path of every call, so it is not done; the token closes it.
    - The key rides in the query string of every webhook URL, so it also shows in Twilio's request inspector and in Workers Logs (observability is on in `wrangler.jsonc`). Set the token as soon as someone can copy it from the Console.
31. **New endpoints (not in SPEC section 3):** `POST /calls/:id/hold`, `POST /calls/:id/resume` and `POST /calls/:id/warm-transfer {to_user_id}`. `:id` works as it does for `/transfer`. Each one answers `{ok:true, held, call_id}`, and warm transfer adds `customer_held` (item 47):
    - `held` is `true` after hold and `false` after resume. After warm transfer it is `true` when the call had to be moved (the customer hears hold music until the teammate answers, then all three talk) and `null` when the hold state did not change:
      - the customer was on hold: they STAY on hold while you and the teammate talk, and Resume brings them in. From a plain Hold (a conference nobody has started) the Worker first puts the customer on a Participants hold, because the teammate starting the conference would otherwise connect them into the consult (fixed 2026-09-29);
      - you were talking to the customer in the conference (after Resume): the teammate joins the two of you. SPEC section 3 describes only the first case; the clients already read `null` as "unchanged" and show the right line for both.
    - `call_id` is the `phone_calls` id. An outbound app should switch to it. Once a warm transfer is answered, `client_call_sid` moves to the teammate's leg, and the app's own CallSid no longer finds the call.

    Refusals use the usual codes: `not_found` (not on the call), `bad_request` (ended, a cold transfer ringing, an emergency call, not on hold, still moving, teammate on DND, the 911 callback window), and `twilio_error`. Warm transfer refuses a teammate on DND. A cold transfer sends them to voicemail instead, but here you are still on the line and can choose. A warm transfer pressed while the legs are still moving in after Hold asks for a moment ("The call is still being put on hold. Try again in a moment.") and rings nobody.

    **The 911 callback window (added 2026-09-29, plan section 14).** For 60 minutes after a 911 call from a number, hold, warm transfer and cold transfer are refused on inbound calls to it ("For an hour after a 911 call from this number, its calls can't be put on hold or transferred."). Each could end in the builder's voicemail (a customer left alone in the conference, a teammate on DND), and the dispatcher's callback must never go there. Resume is never refused. Outbound calls are not affected.
32. **Design (b) of plan 9C, as built.**
    - **Outbound calls:** the Dial now has an action URL, `/voice/after-dial?stage=out`. That branch never rings anyone and never plays voicemail. If the call is in its conference, the app's leg joins it; otherwise the leg hangs up, which is what the Dial did before.
    - **Inbound calls:** after-dial has a new step 0. When `transfer_state = 'conference'`, the customer gets the same `<Conference>`, never voicemail or a hang-up.
    - **Moving a call into its conference:** the Worker redirects the **child** leg of the plain Dial. Inbound, that is whoever answered. Outbound, it is the customer, or the teammate once a cold transfer has handed the call on. The parent leg follows through the Dial's action.
    - **The conference:** it is named after the `phone_calls` id.
      - Customer: `startConferenceOnEnter=false`, `endConferenceOnExit=true`, Twilio's default hold music.
      - Our person: `start=false`, `end=false`, silence (`waitUrl=""`). A call that has just been moved is therefore on hold.
      - Teammate (warm transfer): `start=true`, `end=false`, added with the Participants API.
    - **Hold and resume** ("started" is item 56, never Twilio's REST status):
      - Hold in a conference uses Participants `Hold=true` on the customer unless they are on one already, also when nothing proves it started (item 56).
      - Resume, unless the conference has started, brings our leg back in with `start=true`, then takes the customer off a Participants hold (`Hold=false`) only when they are on one. The redirect goes first, so a failed Resume leaves a held customer held.
    - **A move that fails** (added 2026-09-29). The claim is written before the redirect, so after-dial can already have answered the parent with the conference. What the failed redirect left behind decides:
      - the leg being moved had already ended (a hang-up or drop as the button was pressed): the claim goes back and the parent leg is ended too, as a plain call ends when one side hangs up. Never a customer alone in a conference nobody will join. Skipped if a cold transfer took the call meanwhile. The app gets `bad_request` "That call has already ended."
      - the request got no answer (network) but the leg is in the conference: the claim is kept and the press succeeds (`hold_answer_lost` / `warm_transfer_answer_lost` at `warn`).
      - otherwise: the claim goes back, as before.
    - **Once in the conference:** the call stays there until it ends. A cold transfer is allowed from the conference (`transfer_state` goes from `conference` to `transferring`). It redirects the customer, which ends the conference for everyone else.
    - **When someone leaves:** every conference reports `leave` to `/voice/conference`. When someone other than the customer really hangs up (a leg that was only redirected is still live and is ignored) and the customer is alone:
      - The customer goes to voicemail if they were waiting, meaning held or in a conference that never started.
      - Otherwise the customer is hung up.
      - A warm-transfer teammate who never answers (`/voice/status?leg=warm`) leaves a customer who is alone in voicemail.
      - A conditional clear of `transfer_state` means only one of those events acts.
      - **Second trigger (added 2026-09-29):** the status callback of the leg that holds the call (`client_call_sid`: `leg=client`, `cell`, `warm`, or the outbound app leg) reporting a final status runs the same check, leaving that leg out of Twilio's list. The leave event alone could strand the customer: it is skipped while Twilio still reports the leg live, and a failed REST read was only logged. Failures log `conference_backstop_failed`.
    - **Handed over on hold (added 2026-09-29).** SPEC: the transferrer hanging up leaves the customer with the teammate. When the customer is on a Participants hold and the only other person left is the teammate who answered the warm transfer, the customer is taken off hold (`handed_over` event): when the transferrer leaves mid-consult, or when the teammate answers after the transferrer has gone. If the teammate is the one who leaves, the customer stays on hold for the transferrer to Resume. So does a teammate who never answered: Twilio sends a leave for an unanswered Participants-API leg too, and that leave (a leg that ended `no-answer`, `busy`, `canceled` or `failed`) hands nothing over and prefers voicemail, as the leg's own status callback does (fixed 2026-09-30: it used to take the customer off hold while the transferrer's app said On hold).
33. **Row semantics in the conference.**
    - **Teammate answers a warm transfer:** `answered_by` moves to them, `transferred_from` keeps whoever handed the call on, and `client_call_sid` becomes the teammate's leg. This only happens while `transfer_state = 'conference'`. A teammate who answers after the call has left its conference is hung up.
    - **Our person's leg ending:** while the call is in its conference, this no longer closes the row. The customer's leg ending closes it. The outbound customer leg now also clears `transfer_state`.
    - **Warm transferrer:** they may hold, resume or transfer while the call is in its conference, not after.
    - **Events:** `hold`, `resume`, `warm_transfer`, `warm_transfer_missed`, `handed_over`, `conference_voicemail` and `conference_ended` go into `phone_call_events`.
34. **Voicemail transcription** is behind env `TRANSCRIBE=on` (default `off`). It adds `<Record transcribe="true" transcribeCallback=".../voice/transcription?call=...">`, and the callback stores `phone_voicemails.transcript`.
    - If the transcript arrives before the voicemail row, it retries briefly and then creates the row with the transcript. The later voicemail upsert keeps it.
    - `GET /calls` and `GET /threads/:key` add `transcript` to the `voicemail` summary. This is additive.
    - Twilio only transcribes English recordings of 2 s to 2 min, so a longer message gets no text.
    - The `voicemail_transcription` meter is not charged by anything yet.
35. **Wallet floor.**
    - **When it applies (changed 2026-10, migration 259):** only while `PHONE_USAGE_METERS=on` AND `voice_minute` is armed in the database (`phone_usage_armed`). With the env rail off the database is not asked at all.
    - **The check:** one RPC, `wallet_usage_gate(client, 'voice_minute')`, the same answer the texting path gets (`_shared/usageGate.ts`). Outbound calls are refused below `phone_billing_settings.floor_cents` (default 500; it was the env var `WALLET_FLOOR_CENTS`, now removed). The balance compared is `balance_cents - held_cents` minus the sub-cent remainder rounded up, and no wallet row counts as zero.
    - **Exempt:** tenants with `metered_exempt` or `billing_exempt` are never refused.
    - **The refusal:** TwiML `<Say>` ("Your wallet is empty. Add funds in Structure Studio under Settings, Billing.", or with auto top-up on "Your wallet is being topped up. Try again in a minute." after asking `wallet-autotopup` for a top-up) and a `failed` row with `error_code = wallet_empty`, logged at `info`. `/token` reports the same verdict as `wallet: {state, topping_up}`.
    - **Failures:** a failed read allows the call and logs `wallet_floor_check_failed` at `warn`.
    - **Latency:** the RPC runs in the same parallel round as the minute cap, so it adds no round trip. Inbound calls and 911 never reach this check.
36. **MMS.** **Sending photos is not built.** `_shared/smsSend.ts` → `twilioSms.ts sendSms` posts `Body` only, and a second send path would mean a second set of texting rules. `POST /sms/send` therefore refuses a non-empty `media_urls` with `bad_request` ("Sending photos isn't available yet. Send the text on its own.") instead of dropping the photos without saying so.

    **Viewing** works: `GET /media/:messageId/:index` streams one inbound file.
    - **Scope and login:** it applies the same thread scope as `GET /threads/:key` and answers `not_found` for outbound texts. The login is the `Authorization` header only, as SPEC section 3 says ("Bearer only"); `?access_token=` is refused (changed 2026-09-29: no client used it, and a token in a URL lands in logs).
    - **Twilio fetch:** it uses the API key against `api.twilio.com`, with the path built from SIDs only. It follows Twilio's redirect to the signed file by hand, **without** our Authorization header.
    - **Headers:** only image, video or audio types are shown inline; everything else is sent as an `application/octet-stream` attachment. Every response gets `nosniff` and `CSP: default-src 'none'; sandbox`.
    - **Where the media SID comes from:** `sms_messages.media` when that column exists (proposed, below). Otherwise Twilio's list of the message's media, read through `provider_sid`, whose order may not be the order the photos were attached in (it cannot differ for a single photo).

    **Proposed column, for the backend lane:** `alter table public.sms_messages add column if not exists media jsonb;`. It holds an array in `MediaUrl{N}` order of `{"sid":"ME...","content_type":"image/jpeg"}`. `sms-inbound` would write it from `MediaUrl{N}` (keeping only the `ME` SID from the URL) and `MediaContentType{N}`, with the same retry-without-the-column fallback `numMedia.ts` uses. Store SIDs, never full URLs.
37. **Monthly line fee (`phone_line_monthly`).**
    - **When it runs:** in the daily cron, but only when `PHONE_USAGE_METERS=on` **and** its meter is active and priced. That is one rail more than asked, matching the usage charges (item 24) so that no cent moves on a DB flag alone. Arming it means turning on both.
    - **Who pays:** once per tenant per UTC month, charged in advance with no proration. A tenant has a line when its phone switch is on and it holds a voice-enabled number that has not been released.
    - **Idempotency:** the key is `phone_line_monthly:<client_id>:<YYYY-MM>`. One ledger read skips tenants already charged that month. Exempt tenants are skipped.
    - **Failures:** a failed charge is logged (`phone_line_fee_failed`) and retried by the next day's run.
    - **Cron:** each job now runs on its own, so a retention failure no longer skips billing.
38. **APNs topic per build type.**
    - A `dev` device uses `APNS_BUNDLE_ID_DEV`, or `APNS_BUNDLE_ID` if that is unset. For the whole individual-account period both builds share the `.dev` bundle id, so one secret is enough.
    - A `prod` device uses `APNS_BUNDLE_ID` only. It never falls back to the dev topic.
    - A build type with no topic is skipped and logged (`push_apns_not_configured_dev` / `_prod`).
    - Apple's `DeviceTokenNotForTopic` / `TopicDisallowed` is logged as our misconfiguration (`push_apns_wrong_topic`), and the device is kept.
    - What this does not cover: the `.p8` key belongs to one Apple team. If dev builds stay on the individual team after production moves to the organisation team, the Worker will also need a per-build-type key, key id and team id.

## Not verified here (phase 5, needs a real call)

39. That Twilio requests the parent leg's `<Dial action>` when the **child** leg is redirected, on both inbound and outbound calls. The plan's design (b) depends on this. If it does not happen, the parent would fall off the end of its TwiML and hang up. Test hold on both directions before anyone uses it with a customer.
40. That `waitUrl=""` gives silence. That Twilio's default `HoldUrl` / `waitUrl` music plays (`HOLD_MUSIC` in `src/conference.ts` is the documented default `waitUrl`). That a conference that has not started gives neither side the other's audio.
41. That the Participants API accepts the conference's friendly name when adding a participant. That custom parameters on `To=client:<identity>?call_id=...&transferred_by=...` reach the teammate's Voice SDK the way `<Parameter>` does.
42. That a leg redirected out of a conference (resume) reports `participant-leave` while its call is still `in-progress`, which is how it is told apart from a hang-up.
43. That Twilio's media redirect target accepts a request with no Authorization header (it is a signed URL), and that `GET /Messages/{MM}/Media.json` lists media in attachment order.
44. That the Participants API accepts `Hold=true` on a participant in a conference that has **not started** (warm transfer from a plain Hold), and that the teammate starting it then leaves that customer on hold music. If Twilio refuses, the warm transfer fails with `twilio_error` and rings nobody, so the consult never leaks; it would just not be offered from a plain Hold.
45. That a teammate the Participants API is still ringing appears in the conference's participant list (status `queued`, `ringing` or `connecting`). "The customer is alone" relies on it: if a ringing teammate is not listed, the transferrer hanging up during the ring sends the customer to voicemail instead of waiting for the teammate (or, if they were talking in a started conference after a Resume, hangs up on them). Item 52 tried to cover that second case from the call's events and was withdrawn.
46. That a Participants-API call to `client:<identity>?call_id=...` reports `to` as `client:<identity>` (with or without that query; both parse). The unsigned warm-answer check (item 30) depends on it; if Twilio reports something else, key-only mode refuses every warm hand-over (`warm_answer_unverified`) until the token is set.

## Added 2026-09-29: warm-transfer follow-ups from the client review

47. **`customer_held` on `POST /calls/:id/warm-transfer`.** `true` when the customer is held as a participant through the consult: you and the teammate talk privately and Resume brings the customer in. This is the case from a plain Hold (the Worker holds them first, item 31) and from a Hold after Resume. `false` when they are not: a plain call just moved (they wait on music and are connected when the teammate answers), or a customer you were talking to after Resume (the teammate joins the two of you). `null` only when the participant list could not be read; the teammate is still rung.
    - **Refusals that know where the customer is say so beside `error`** (`{ok:false, error, held, call_id}`, phone-core `refusalHeld`). `held: true` after a move whose teammate could not be rung (the "press Resume" sentence), and after a failed ring from a conference where the customer is held. `held: false` for the Hold race in item 50. `ok` and `error` can never be replaced by these.
48. **A missed warm leg tells the apps at once.** A teammate who does not answer (no-answer, busy, failed, canceled) changed nothing on the row, so the realtime broadcast never fired and the apps waited out their 35 s. Now `/voice/status?leg=warm`:
    - writes `warm_transfer_missed` FIRST, now with the leg's CallSid (`sid`);
    - finishes the customer if they are alone, leaving that leg out of Twilio's list (it has ended, whatever the list says), always voicemail;
    - accepted on `?key=` alone (the live Worker today), does all this only when Twilio's record of that CallSid agrees: the leg has ended and its `to` is the identity of the `user` in the URL (the check the answer path already makes, item 30). Otherwise it logs `warm_miss_unverified` (`warn`), writes no event, does not touch the row, and still finishes a customer Twilio lists as alone, without leaving any leg out (the behaviour before this item). A forged miss naming a leg still in the call (the one who handed it on, talking to the customer) therefore cannot make the customer look alone;
    - otherwise writes `transfer_state` back to the value it already has (`'conference'`, guarded on it still being `'conference'`, so nothing that moved the call on meanwhile is undone). The broadcast trigger is `AFTER INSERT OR DELETE OR UPDATE ... FOR EACH ROW` with no `WHEN` clause (read from the live database on 2026-09-29), so a same-value update still broadcasts. Voicemail changes the row by itself, so it needs no second write.
    - **No migration 255 is needed for this.** The apps learn the outcome from `GET /calls` (item 51).
49. **Transfer legs name the real caller.** Warm and cold transfers both send `customer_e164` (the customer's number: `from_e164` inbound, `to_e164` outbound, only when it is a whole North American number, so a withheld caller sends none) and `contact_id` (when the call has one), beside `call_id` and `transferred_by`. A cold transfer sends them as `<Parameter>`s. A warm one sends them on the client address, URL-encoded (`customer_e164=%2B1...`), because the Participants API has no `<Parameter>`. SPEC section 3 already tells the apps to read them.
50. **Hold pressed while a Resume is still landing.** Resume in a conference nobody has started redirects our leg back in with `startConferenceOnEnter=true`. Until that leg lands nothing proves the conference started (item 56), and Hold used to answer `held:true` without doing anything, after which the conference started and connected the customer. Now:
    - Resume on that path writes its `resume` event before it answers, instead of in the background.
    - Hold on a conference not proven started holds the customer through the Participants API (as a warm transfer from hold does, item 44; since 2026-09-30 whether or not a Resume is landing, item 56), so they stay on hold when the conference starts. It reads the Worker's latest `hold`/`resume` event for the call since its latest cold transfer (`transfer` event): a Resume from before one was in a conference that the cold transfer ended, and the one Hold is pressed in now was entered by a move. The apps' own timing marks (`source: "app"`) never count. If it is a `resume`, the `hold` event records `after_resume: true` and a refused hold is reported as below.
    - With a Resume landing, if that hold answers 404 (the customer's leg is not in the conference either), the Worker refuses: `bad_request` "The call is still coming off hold. Press Hold again in a moment." with `held:false`. Any other Twilio failure gives `twilio_error` "Hold didn't work. You're still on the call." with `held:false`. With none landing, 404 and 400 answer `held:true` (item 56).
    - If the event read fails, it counts as no Resume landing.
51. **`GET /calls` (and `GET /threads/:key`) rows add `warm`.** It appears only on a live call in its conference (`in_progress`, `transfer_state = 'conference'`) that the Worker rang a teammate into: `{to_user_id, state: "ringing" | "missed" | "answered", at}` for the latest warm transfer in the call's current conference. A cold transfer ends the conference, and the teammate who takes the call can move it into a new one under the same name, so warm transfers from before the latest `transfer` event are never reported. `answered` means `answered_by` is that teammate. `missed` means a `warm_transfer_missed` for the same leg; the CallSid ties the two, because a fast decline can be written before the `warm_transfer` event. It costs one `phone_call_events` read, and only on pages that have such a call. If that read fails, `warm` is simply left off. **The apps must switch to it:** while a warm transfer rings, `warm.state === "missed"` for that teammate means no answer (clear the transfer and say so), and the 35 s limit stays as the fallback.
52. **Withdrawn (review, 2026-09-29): no voicemail for an "untaken" warm transfer.** For a few hours the Worker sent a customer left alone while talking to voicemail whenever the latest warm transfer on the call had not been taken (ringing or missed). That read every warm transfer the call ever had, including one missed before a Resume or before a cold transfer, so after a miss, Resume and an ordinary goodbye the customer heard the voicemail greeting and a stray voicemail could be filed. SPEC section 3 says the opposite: after a miss the apps clear the transfer and say "You're still on the call", and hanging up after that is an ordinary end. So a customer left alone is finished as before: voicemail if they were waiting (held, or the conference never started), hung up if they were talking. The cases it meant to cover are already handled without it: a teammate still ringing is in the participant list, so the customer is not alone (item 45), and a teammate who misses while the customer is alone sends them to voicemail from their own leg's status (item 48). No `conference_voicemail` event carries `warm_untaken` any more.
53. **`?access_token=` on `GET /voicemails/:id/audio` stays, for installed extension builds only.** The apps in the phone repo now send the header only (checked read-only on 2026-09-29): the extension fetches the audio with it and plays it from a `blob:` URL (`api.voicemailAudio`), the mobile app hands it to expo-audio (`voicemailAudioSource`), and phone-core has no `voicemailAudioUrl` any more. Extension builds installed before 2026-09-29 still play voicemail through `<audio src>` with the token in the query, so the Worker keeps accepting it. Nothing in the code is left to change: remove it once those builds are gone (SPEC section 3). `/media` stays Bearer only.

## Fixed 2026-09-30: "has the conference started?" (found on a live call)

56. **Twilio's REST conference status is not a start signal.** On a live call a plain Hold (both legs in with `startConferenceOnEnter=false`, the customer on wait music) read `in-progress`, both legs `connected`, `hold=false`, for 20 s and more. The Worker read `init` as "nobody has started it" and anything else as "started", so:
    - Resume sent Participants `Hold=false` to a customer who was not held. Twilio refused it (HTTP 400, code 400; `resume_failed`), the app said "Couldn't take the call off hold" and the customer stayed on wait music.
    - Warm transfer from a plain Hold did not hold the customer first, so the teammate starting the conference connected the customer into the private consult.
    - The agent hanging up during a plain Hold hung the customer up instead of taking a voicemail.
    - The Hold-while-Resume-lands guard (item 50) never ran.

    **Now** `conference.ts hasStarted` is the only answer, and nothing reads the status:
    - **Twilio's `start` event.** Every way into a conference asks for `start leave` (TwiML `statusCallbackEvent`, and `ConferenceStatusCallbackEvent` on the warm-transfer add; Twilio takes them from whichever leg creates the conference). `/voice/conference` records `conference-start` as a `conference_started` event with `{conference_sid}`. Duplicates are harmless and nothing removes it. It is keyed by ConferenceSid because a call can have one conference after another, and the apps' own marks (`source: "app"`) never count. Accepted on `?key=` alone it is recorded only when Twilio's participant list proves the same (below); otherwise `conference_start_unverified` at `warn`.
    - **A warm-transfer teammate answering** (added after review). They join with `start=true` beside the customer, so the conference has started. `warmLegStatus` records the same `conference_started` once the answer counts (unsigned, only after the checks in item 30), so a conference whose starter has hung up stays proven without Twilio's start callback, which is not verified live. A failed insert there logs `conference_start_record_failed` and never stops the hand-over. From the start callback, a failed insert throws (`conference_event_failed`) instead of passing as recorded.
    - **The participant list**, checked first: a `connected` leg with `start_conference_on_enter=true` beside another `connected` leg is Twilio's documented start condition. It covers the moment before the event arrives. Its absence proves nothing (the leg that started it may have left).
    - "Not started" therefore means NOT PROVEN, and each caller does what is safe either way: Resume brings our leg back in with `start=true` (into a conference that had started, only a leave and re-join, which the leave handler ignores); warm transfer holds the customer first; a customer left alone gets voicemail; Hold holds the customer through the Participants API too (a started conference whose starter left with no start recorded has the two of you talking), and with no Resume landing (item 50) a 400 or 404 there answers `held:true`, because a conference that has not started is hold.
    - Resume sends `Hold=false` only to a customer on a Participants hold. A second Hold, or a warm transfer with the customer already held, sends no second `Hold=true`.
    - Conferences created before this deploy never send `start`; for those the participant list is the only proof.

    **Still not verified live:** that Twilio sends `conference-start` to the callback set by the first leg in (TwiML or Participants API); and item 55, now the main open question. The live 400 was on `Hold=false` for a leg that was not held; whether Twilio also refuses `Hold=true` in a conference that has not started is unknown. If it does, warm transfer from a plain Hold answers `twilio_error` and rings nobody (the consult never leaks), the Hold race answers `held:false`, and any other Hold not proven started answers `held:true`. Probe it on a test call before relying on warm transfer from hold.

## Added 2026-10-02: moving a live call between the person's devices (migration 260)

57. **New endpoints (SPEC section 3 calls; the phone repo's SPEC is updated by the apps stream).** All take `:id` as the call id or a leg's CallSid, and every answer carries `call_id`.
    - `POST /calls/:id/handoff {to: "chrome"|"mobile", leg_sid}` → `{state: "ringing", key, to, call_id}`. `leg_sid` must be the leg holding the call (`client_call_sid`), and the caller must hold it (`answered_by`, or `placed_by` on an outbound call not handed on). Refusals: `not_your_call` 403, `not_live` 409, `emergency` 409 (a 911 call, or an inbound call in the hour after one), `transfer_in_progress` 409 (a cold transfer, or a warm one still ringing), `handoff_in_progress` 409, `no_target_device` 409, `ring_failed` 502 ("Couldn't ring your phone. You're still on the call."; nothing changed). These seven codes are new; clients switch on `code`.
    - `POST /calls/:id/handoff/cancel {key}` → `{state: "canceled"}`, from either device (item 58); with no ring under that key, how the move stands.
    - `GET /calls/:id/handoff` → `{state, to}`, state `ringing | connecting | done | missed | failed | canceled | none`.
    - Status and cancel also find the call by the CallSid of the leg the latest move took it FROM (`handoff_from_sid`). An outbound app that never learned the call id watches its move by its own leg's CallSid, and the swap moves `client_call_sid` off that leg just before ending it: without this, the old device's "how did my call end?" was a 404 at exactly that moment and it could not tell a move from a hang-up. Starting a move still needs the leg that holds the call.
    - `GET /handoff/pending?for=chrome` → `{offer: null | {call_id, key, customer_e164, contact_id, contact_name, direction, answered_at, held, expires_at}}`. `expires_at` is extra: the ring's 45 s end, so the extension can stop ringing without polling. `contact_name` follows the contacts row scope; the number is sent either way (they are on the call).
    - `POST /voice/handoff` (Twilio) answers the ring placed to the phone. `/voice/outbound` with `HandoffCall` + `HandoffKey` is the computer answering; it returns before the 911 check, `insertCall`, the daily minute cap and the wallet floor, so a move never adds a `phone_calls` row and is never refused for minutes or money.
    - `POST /token` adds `features: {handoff: true}`. `GET /calls` rows add `handoff_state` and `handoff_to` (only while a move is under way, else null).
58. **Choices where the build contract left room.**
    - **"While `handoff_state` is not null" reads as "while a move is under way":** not null AND `handoff_at` within 45 s. `handoff_at` is the ring's start, then the answer's time (set by the same update that goes to `connecting`). Past that the move is over whatever the row says, so a lost callback can never block Hold, Resume, both transfers or the next move for good. `GET /calls/:id/handoff` reads a stale `ringing` as `missed` and a stale `connecting` as `failed`.
    - **after-dial `stage=out` hangs up only the leg a move took the call FROM** (`CallSid = handoff_from_sid` and it is no longer `client_call_sid`), not every `CallSid ≠ client_call_sid`. Before the hand-over that leg still joins the conference, as any outbound app leg does after Hold, so a move that fails after the customer was redirected still leaves the call on the old device. (The broader rule would also have changed an existing after-dial case.)
    - **`finishIfAlone` and the two legs of a move.** While a move is `connecting`, the old leg leaving does nothing (the new leg may not be listed yet). Once a move leg no longer holds the call (the old leg after the move, the new leg after a failed one), its leaving never triggers HANDED OVER ON HOLD: without this, the old leg leaving a call whose customer was on a Participants hold took the customer off hold. A customer it leaves truly alone is still finished as before.
    - **A decline is a cancel, with its own reason.** Cancel from the device being rung (`Origin: chrome-extension://` or `x-sss-client: extension` for a computer offer, the way `/sms/send` tells the apps apart; no Origin for the phone) records phase `canceled`, reason `declined`; the asking device's own Cancel is reason `canceled`. Both answer `{state: "canceled"}`. The device that asked stops its own watch when it cancels, so a `canceled` it reads is always the other device's no, and the apps word it that way ("The call stayed on this phone."; the extension clears the move quietly). (Integration, 2026-10-03: this stream first recorded a decline as `missed`; both apps were built to the contract's `canceled`, so the Worker was brought back to it.) The phone's Leave on computer cancels first and rejects the ring after; a ring declined through Twilio alone ends `busy`, which `/voice/status?leg=handoff` records as `missed`.
    - **The target device.** The phone counts when `phone_devices` has an `android` or `ios` row with a push token; the computer when there is a `chrome` row. A person whose only phone is an iPhone development build is rung on `<identity>_dev`. The ring goes to the person's identity, so a second, idle computer could ring too (plan Part 2, known risk); whichever answers first takes the call.
    - **`held`** is worked out once, before the claim: a customer on a Participants hold, or in a conference nothing proves has started (a plain Hold), or with no conference yet, is held. A Twilio read that fails, on a call in its conference, counts as held: the new leg of such a call joins waiting, so a customer who really is waiting would otherwise leave the person in silence with no Resume, while Resume on a customer who is in fact talking does nothing. It rides the phone's ring as `held=1|0` and the `offered` event (for the computer's offer). Hold and Resume are refused during the ring, so it cannot change before the answer.
    - **The call ending during the ring stops it** (either the holder's leg or the customer's, from `/voice/status`): cleared, the phone's ring `canceled`, phase `canceled` with reason `call_ended`.
    - **Events.** Every step is a `phone_call_events` row of type `device_switch` with `data.phase` `offered | done | missed | failed | canceled`. `offered` is written before the ring (so a fast `missed` is never older than it) and has no `sid`; the ring leg's own status events carry it. `done` has `sid` = the new leg (usage billing collects a call's legs from `data.sid`), `from_sid` = the old one, and `ms`. The key is never written to an event.
59. **Verified against Twilio's documentation (2026-10-02): custom parameters on a REST call to a client.** "How to share information between your applications" documents creating a call with `To=client:agentBob?displayName=Alice&customerID=...` and reading the values from `TVOCallInvite.customParameters` (iOS) and `CallInvite.getCustomParameters()` (Android), available from SDK 3.0; the Voice JS SDK reads `call.customParameters`. 61. **Review fixes (2026-10-03): the switch never hands the call to a leg that is gone, and never strands the customer.**
    - **The new leg is checked again before the switch.** completeHandoff looked at the new leg once (step 1). If the person ended it while the other side was on its way in (it hears silence until then), its leave changed nothing (the old leg still kept the customer company) and its status callback was ignored (it was not the holder yet), so the swap handed the call to a dead leg and the old leg was ended: the customer got voicemail mid-call, or was hung up, and the old device read `done`. Now the new leg must still be live (Twilio's call record) and connected in the conference before a plain call's child is redirected and again right before the swap; a failed read does not stop the switch. After the old leg is ended, the customer is looked at once more (finishIfAlone), so a leave let pass while connecting can never leave them on hold music.
    - **A failed switch on a plain call that had already moved starts the conference for the old leg** (Resume's start=true) when nothing proves it started: the new leg, the one that would have started it, left before anyone joined, and the customer would hear hold music and the old device silence.
    - **An outbound plain call's customer is moved first (step 0).** There the customer is the child of the old app leg's Dial, so the old device hanging up during the wait for the new leg (Hang up pressed once the other device answered, an iPhone's side button) took the customer down with it; inbound was already safe (after-dial step 0). The redirect now comes before the wait, so the window is the one request between the answer and the redirect. The customer may hear a moment of hold music until the new leg (start=true) joins.
    - **A failed switch puts the conference claim back only while the plain Dial is really there.** If the old leg ended while the switch was connecting, after-dial step 0 has taken an inbound customer into the conference; putting `transfer_state` back to null then left them on hold music with nothing watching. The claim is now kept when the old leg has ended or the customer is listed in the conference, and the customer is finished like any other left alone (voicemail if waiting).
    - **The handoff columns outlive the move, so `finishIfAlone` reads them against the holder now.** A leg is a "switch leg" (its leaving never takes a held customer off hold) only while it lost the call TO the switch: the old leg while the new one holds it, or the new leg of a failed switch while the old one does. Before, any earlier move attempt (missed, canceled or done) made the leg that later warm-transferred the call exempt, and the customer stayed on hold with the teammate for good.

## Added 2026-10-03: the Chrome extension's error reports carry no direct identifiers

64. **`/log` stores no direct identifiers for the Chrome extension** (sources `my-synergy-phone-extension` and the older `sss-phone-extension`; `src/logPrivacy.ts`). The extension's privacy policy claims the Chrome Web Store's Limited Use rules, under which people here may read user data only with the user's consent, for security, to comply with the law, or aggregated and anonymised for running the service, and `app_errors` was read row by row. So for those two sources:
    - `client_id` is null and `context.user_id` is gone. `context.user_ref` and `context.client_ref` take their place: HMAC-SHA-256 under the new secret `LOG_PSEUDONYM_KEY` of `user:<user id>` (lowercased) and `client:<client id>`, hex, cut to 24 characters. One person's repeated errors still group, and `count(distinct context->>'user_ref')` says how many people an error hits. The key stops anyone recomputing a ref from a user id they hold, and with it `scripts/log-ref.mjs` turns a person's ids into their refs, for when they ask for help (SETUP.md section 10). It does not make the rows anonymous (the reading rule below). A key that is unset or shorter than 32 characters means no refs at all (never the raw ids, never an unkeyed hash, which anyone holding the user list could recompute), the report is still saved, and `log_pseudonym_key_missing` is logged at `warn` once per isolate. A person with no business gets `user_ref` only.
    - `context` keeps only the keys the extension is known to send (audited from every `logger.log` / `deps.log` call site, 2026-10-03): `where`, `repeats`, `code`, `twilio_code`, `reason`, `type`, `surface`, plus the Worker's own `_truncated` and `bytes` and `app_version`, with plain values only. Anything else (an `identity`, a `user_id`, a `call_sid`, a nested object) is dropped and only its key is listed in `dropped`, so a newer build sending a new key shows up as a key to add here rather than vanishing quietly.
    - The message, the code, `app_version` and every kept string have emails (also `%40`), phone numbers (E.164 and North American ten or eleven digits, however punctuated), uuids (with or without hyphens), Twilio identities (`u_<hex>_g<n>`) and SIDs, and Supabase login tokens replaced by `[redacted]`, before the text is cut to length so half a number is never left behind. Twilio error codes, versions and millisecond timestamps survive.
    - Call SIDs are dropped too. A SID alone names nobody, but it joins to `phone_calls`, which names the customer and the person, so it would undo the pseudonym. A report about a call keeps `where: "call"` and its codes. That does not stop a join by time: a report's time and codes can still be lined up with the person's calls, which is how a call is found when they ask for help, and also why these rows are only pseudonymous.
    - Kept as before: `source`, `severity`, `user_agent` (a browser string; Chrome's reduced user agent carries the major version and platform only), the per-person rate limit (it lives in memory and is never stored), `url` (always null here).
    - Free text cannot be proved to hold no name: a JavaScript error could in principle quote a contact's name. The extension's messages are error messages from its own code, the Worker and the Twilio SDK, which carry ids and numbers (now redacted) but not names.
    - **Pseudonymous, not anonymous, so the rows are read only in summary.** Anyone who can query the database can line a report's `created_at` and its `where` or `twilio_code` up with `phone_calls` or `phone_call_events`, which name the person, and in a small user base one match names every report under that ref. Limited Use allows reading for running the service only when the data is aggregated and anonymised, so routine triage of these two sources, and of the Worker's own `edge:phone-api` rows, runs the grouped query in SETUP.md section 10 (counts by source, code, severity and a message scrubbed again as it groups; no ref, no id, no time) and opens single rows only with the person's consent, for security or for the law. This is a rule for the people (and agents) who read the table, not something the code enforces.
    - The Worker's own rows fall under that rule because they are written while it serves everyone's calls and texts, the extension's users included, and they carry business ids, call ids, a contact id (`sms_send_*`), a user id (`emergency_blocked`) and, for an unhandled fault, the request path (`/threads/n:<number>`, `/threads/<contact id>`, `/calls/<call id>/...`); a row does not say which app was involved. They are not pseudonymised: fixing a server fault needs its ids, and most of them come from Twilio's webhooks and the crons, where nothing says which app placed the call. The Worker's Cloudflare logs (observability is on) carry the same ids and are read the same way.
    - Rows from before this change hold the ids in `context` AND in `message` (a Twilio identity is the user id, and the Twilio SDK's messages quote it), so stripping keys would not do. They are deleted once, resolved or not, after a summary by code is kept (SETUP.md section 10 step 4).
    - Readers: nothing in this repo reads `client_id` or `context.user_id` of these rows. No RLS policy, trigger or constraint involves them (`app_errors` is service-role only, `client_id` nullable since 028). admin-catalog's tenant wipe deletes by `client_id`, so it no longer reaches the extension's reports (SETUP.md section 10 says how to find a business's rows by `client_ref`). The mobile app's reports (`my-synergy-phone-mobile`, `sss-phone-mobile`) are unchanged.

## Added 2026-10-04: call recording, transcripts and summaries (release B2, migration 263)

65. **Recording is REST-only, announced, and armed per call.** SPEC section 3 said "Recording: off". The plan (B2) and its decisions (2026-10-04) replace that with: one dual-channel recording per call on the customer's leg, started through Twilio's REST API when someone answers (`src/recording.ts`); never a TwiML `record` attribute (`test/outbound.test.ts` still asserts there is none). A call may be recorded only when it is armed: `CALL_RECORDING` exactly `on`, the business's switch on (owner only), the announcement on (locked on), and not an emergency call or the 911 callback window. `phone_calls.recording_armed` is written true only when the TwiML the call ran carried the announcement, so a setting turned on mid-call cannot record a call that never heard it. Where the plan left room:
    - The announcement is said before the first inbound ring and before an after-hours forward; re-rings and forwards after a missed ring do not say it again (the caller heard it), but their `<Client>`s carry `recorded=1` and a forwarded cell's screen says "This call is recorded." A voicemail-only answer (nobody available, the switch off, after hours to voicemail) is never armed.
    - Outbound, it is the `<Number>`'s whisper `url` (`/voice/notice?call=<id>&c=<business>`), read by business id (one database read) rather than by call id (two). A read that fails says the standard sentence: the call is armed, or the URL would not be on it.
    - "and transcribed" is said only while transcription will really happen: the business left transcripts on AND `CALL_TRANSCRIBE` is `on`. A business's own sentence must say the call is recorded and not deny it (portal-settings refuses one that doesn't; `noticeText` speaks the standard sentence instead of a stored one that fails `_shared/recordingNotice.ts`).
    - The start also resumes: a cold-transfer teammate answering a customer whose recording was paused for hold resumes it. A start Twilio refused (4xx) is tried again by the next answer on the call (a transfer), once per answer. A start whose answer was lost or broken (unreachable, 5xx, a 2xx with no SID) may have started a recording, so its row stays `starting`: Twilio's callbacks bind the SID, or the backstop settles it, and no second recording is started (review, 2026-10-04).
    - Hold pauses (PauseBehavior skip) and Resume resumes, both awaited before the press answers so a quick Hold then Resume cannot land out of order. A customer handed over in the conference (HANDED OVER ON HOLD) is resumed too. A warm transfer from a plain call does not pause: the customer hears music only while the teammate rings, and the conference connects all three when they answer. That stretch is recorded (and transcribed), and the privacy pages and the Settings card say so ("except while the call is being passed to a teammate").
    - Every redirect to voicemail stops the recording first, awaited: a customer left alone in the conference and after-dial's voicemail on a call that is armed (a transfer nobody took). A stop that fails is logged and the redirect still happens. A cold transfer to a teammate on DND PAUSES it (PauseBehavior skip) before the redirect and stops it once the redirect has landed: that redirect can fail with the call still going ("You're still on the call"), and a stopped recording can't be resumed, so then it is resumed instead (review, 2026-10-04).
    - Pausing, resuming and stopping ignore the `CALL_RECORDING` rail (a recording already running is still paused and stopped after the rail is turned off); starting one obeys it.
    - The channel map (`CHANNEL_MAP`: channel 0 the customer, 1 the team) is what Twilio documents for a one-leg recording with RecordingTrack both; it is kept on each row and must be confirmed on the verification call.

66. **The recording callback and the backstop.** `/voice/recording?rec=<id>` takes a callback only for the row's own recording: its stored SID, or (while the start is still in flight) a RecordingSid on the row's own customer leg. Unsigned (`TWILIO_AUTH_TOKEN` unset), a `completed` counts only when `fetchRecording` finds it, and the length is Twilio's; and before an unsigned callback writes anything that binds or settles the row (in-progress, completed, or absent/failed on a row with no SID yet), Twilio's record must show a `StartCallRecordingAPI` recording of this row's customer leg (`recording_callback_unverified` otherwise), because the account holds every business's recordings and an unsigned CallSid is only the request's word (review, 2026-10-04). `absent` and `failed` are stored as such. The plan put the backstop in the voicemail sweep's list; it is a job of its own on the same 15-minute tick instead (`recordingBackstop`), reading only rows still live 10 minutes after their call ended and asking Twilio for that call's recordings, so the sweep fix (section 1) ships alone. The sweep's own "skip any SID in phone_call_recordings" from the plan is not added: the RecordVerb-only filter already excludes every call recording, and the extra read would have tied the sweep fix to migration 263.

67. **Transcripts and summaries.** Workers AI `@cf/deepgram/nova-3` (multichannel, utterances, smart_format, punctuate, `mip_opt_out`) from the minute tick while `CALL_TRANSCRIBE` is `on`, two recordings per tick, with the business's transcript switch read again at transcription time. Lines are "Customer:" / "Team:" from the row's channel map: nova-3's utterances when it gives them, else its words split at pauses over 1.5 s. The transcript is capped at 100,000 characters at a line boundary; `transcript_json` keeps the utterances that fit. A recording shorter than 5 s is not transcribed. Back-off 1, 5, 15, 60 minutes; failed after 5 attempts, at once when Twilio no longer has the audio. `stt_cost_micros` assumes both channels are billed at $0.0052 a minute (an estimate until the verification call). The summary is the `phone-call-summary` edge function (claude-sonnet-5-5, low effort, server-side fallback `default`), asked by the cron with the service key; the function claims the row itself, so a repeat never asks Claude twice. Asked again 2 minutes later while still pending; given up a day after the recording.

68. **API shapes.** Every call in `GET /calls` and `GET /threads/:key` gains `recording`, `summary` and `transcript_status`, always present (null when there is nothing). The plan put the transcript on the call too (8,000 characters); it is left off, because the extension and the phone app both save those rows on the device (IndexedDB, the phone's query cache), where a customer's conversation would sit unencrypted on every team device and outlive the business's retention. The apps read it with `GET /calls/:id/transcript` when someone presses "Show transcript" and keep it in memory only; `transcript_status: "done"` says there is one (a call with no words reads null). `recording.state` adds `processing` for a call that has ended while Twilio is finishing the file. `GET /recordings/:id/audio` plays only a completed recording, mixed to one channel, and has no `?access_token=` door. `GET /calls/:id/transcript` is new. `/token` gains `recording: {on}` and `features.recordings`. Who may hear and read is voicemail's rule (`mayViewCall`). `DELETE /recordings/:id` is not built (P3).

69. **Never logged.** No transcript or summary text reaches a log line, `phone_call_events` (the marks say how many characters) or `app_errors`. Faults about a transcript or summary write carry the database's code, not its message (a Postgres message can quote the row). `test/transcribe.test.ts` and `tests/phone/callSummary_test.ts` plant a phrase in a transcript and check every log, answer and mark for it.
